# Workflows

[Documentation](../index.md) · Reference

Every managed project owns its CI. A project authors GitHub Actions workflows under its own `src/infrastructure/workflows/<concern>/` folder, grouped by concern, and stays independent of where it lives in a workspace. GitHub only runs workflows from the repository's `.github/workflows/`, so `workflows sync` generates prefixed, project-scoped entrypoints there. The authored files are the single source of truth; generated files are never edited by hand, and `workflows sync --check` fails CI when they drift.

## Commands

`workflows` always runs at workspace scope, even while a project is selected: discovery covers every managed project, and generated files belong to the workspace root.

| Usage | Effect |
| --- | --- |
| `workflows` / `workflows list` | List each authored workflow with its project, concern, source, generated target and status, plus stale generated files. Read-only. |
| `workflows sync [--dry-run]` | Create missing and update changed entrypoints, and remove stale generated files, through guarded workspace writes. A dry run returns the planned changes with unified diffs and writes nothing. |
| `workflows sync --check` | Compare without writing. Succeeds with `inSync: true`; otherwise exits 5 with `WORKFLOW_DRIFT`. |

Statuses are `missing` (no generated file yet), `changed` (generated bytes differ from the current rendering), `unchanged` and `stale` (a generated file whose source no longer exists). `list` returns `{ directory, count, inSync, workflows }`; `sync` returns `{ dryRun, workflows, changes }`, where `changes` are the usual created, updated or deleted file changes with revisions and committed `vault.*` events (including `kind: "folder"` records for new `.github` folders). A failing check carries the drifted entries in `error.details.workflows`.

```sh
node bin/forge.js workflows list --json
node bin/forge.js workflows sync --dry-run
node bin/forge.js workflows sync
node bin/forge.js workflows sync --check
```

## Discovery and names

A managed project is a directory under the configured `paths.projects` with a valid `.forge/project.json` marker; see [configuration](configuration.md). Within a project, sync reads files that sit directly in a concern folder and end in `.yml` or `.yaml`:

```text
src/<project>/src/infrastructure/workflows/<concern>/<file>.yml
```

Concern and file names use lowercase letters, digits, `.`, `_` and `-`. Each source generates `.github/workflows/<project>--<concern>.yml` when the file is named after its concern, and `.github/workflows/<project>--<concern>--<file>.yml` otherwise. For example, `src/the-forge/src/infrastructure/workflows/guard/workflows.yml` generates `.github/workflows/the-forge--guard--workflows.yml`. Two sources that generate the same file, such as `check.yml` and `check.yaml` in one concern, fail with `INVALID_WORKFLOW`.

## Transformation

Sync parses each source with the YAML 1.2 core schema, so `on` stays a key rather than a boolean, and keeps every other key, comment and scalar style. For equal input it produces identical bytes. Each generated file:

1. starts with a header naming its source: `# Generated by forge workflows sync from <source>.` The header marks the file as owned by sync;
2. limits `push` and `pull_request` triggers to the project. Without filters, `paths` becomes `<project>/**` plus the generated file itself. Declared `paths` are prefixed with the project directory. A declared `paths-ignore` becomes `paths` that start with `<project>/**` and add each ignored pattern negated, because GitHub rejects both filters on one event. `on: push` and `on: [push, pull_request]` become mappings first. Other events, such as `workflow_dispatch` and `schedule`, are unchanged;
3. sets `env.FORGE_PROJECT_PATH` to the project's workspace-relative directory. `working-directory` applies only to `run` steps, so action inputs such as `cache-dependency-path: ${{ env.FORGE_PROJECT_PATH }}/package-lock.json` use this variable;
4. sets `defaults.run.working-directory` to the project directory, merged into existing `defaults.run` settings. Authored working directories at workflow, job and step level are project-relative and resolve inside the workspace; values containing `${{` expressions are kept.

Authored paths that start with `/` are workspace-relative. Use them for files outside the project, for example `paths: ['**', '/bin/**']` to run a check when the project or the shipped distribution changes, or `paths: ['/**']` to run on every pull request. Patterns starting with `!` keep their negation.

Path filters interact with required status checks: GitHub never starts a workflow whose `paths` do not match a pull request, so a branch protection rule that requires one of its jobs leaves that pull request waiting for a check that never reports. Require only checks of workflows that run on every pull request (`paths: ['/**']`), or let a small always-running job aggregate the path-filtered results; Forge does not generate such a job.

A source that is not valid UTF-8 or YAML, is not a mapping, lacks `on` or `jobs`, or uses an unsupported trigger, path filter or working-directory shape fails with `INVALID_WORKFLOW` and nothing is written.

## Ownership and safety

Sync writes through the guarded workspace. It updates a generated file only at the revision it compared, and creates a missing one only if the path is still free, so concurrent edits fail with `CONFLICT` instead of being overwritten. A file at a generated path without the header was not written by sync: it is never overwritten and fails with `CONFLICT`; move or delete it first. Sync removes a generated file whose source disappeared, but leaves files without the header, such as hand-written workflows, alone.

## In this repository

The Forge, `src/the-forge`, authors its full matrix gate in `src/infrastructure/workflows/check/check.yml` and a `guard` concern that runs `node "$GITHUB_WORKSPACE/bin/forge.js" workflows sync --check` on every pull request. The showcase authors `src/forge-showcase/src/infrastructure/workflows/check/check.yml`, which runs its own `npm ci` and `npm run check` on Node 22.12 and 24. The test suite also runs the same drift check against the checkout. After changing any authored workflow, run `node bin/forge.js workflows sync` from the workspace root and commit the source and generated files together.

See [errors](errors.md) for `WORKFLOW_DRIFT` and `INVALID_WORKFLOW`, and [develop and test](../how-to/develop-and-test.md#platform-matrix) for the platform matrix.
