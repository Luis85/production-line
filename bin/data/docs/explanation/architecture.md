# Architecture

[Documentation](../index.md) · Explanation

## Boundaries

The domain uses the terms **workspace**, **file snapshot**, **revision**, **write plan**, **generator**, and **committed change**. The filesystem is an adapter; Obsidian is not a runtime dependency. A workspace owns fixed `bin` resources and a configurable managed-project directory. Persistent project selection chooses the root for document commands and generators; shared templates/plugins and project management remain workspace-scoped. Command responses identify the executed scope. Revisions describe file content, not elapsed time or a globally ordered version.

Source is organized by layer, then by concern. For example, workflow rules belong in `src/domain/workflows`, their use cases and ports in `src/application/workflows`, the YAML adapter in `src/infrastructure/workflows`, and command translation in `src/presentation/workflows`. A concern does not need a folder in every layer. Paths in this section are relative to the Forge project directory `src/the-forge`; its `src/README.md` maps entry points and placement examples.

The repository is a thin workspace whose managed projects are self-contained. The Forge is one of them: workspace configuration sets the managed-project directory to `src`, the marker `src/the-forge/.forge/project.json` identifies `the-forge`, and the persisted selection names it. File commands then resolve from the project root `src/the-forge`, exactly as in any generated project. The project owns its `package.json`, lockfile, compiler/build configuration, tests, scripts, policies, documentation and authored skills; its build writes the shipped distribution into the workspace `bin/` named by `config.distribution` in `package.json`. Sibling projects such as `src/forge-showcase` keep their own toolchains. Generic release defaults remain `projects` with no selection, and normal builds preserve the checkout's selected project.

Each project authors its CI workflows under `src/infrastructure/workflows/<concern>/`. The `workflows` command family discovers them in every managed project and synchronizes prefixed, path-scoped entrypoints into the workspace `.github/workflows/`; the authored files stay the single source of truth and drift fails CI. Discovery and the transformation are pure application/domain logic over the file repository port; the YAML codec is an infrastructure adapter. See [workflows](../reference/workflows.md).

| Location | Responsibility | Allowed source dependencies |
| --- | --- | --- |
| `src/domain/<concern>/` | Value contracts, path and document invariants, pure analysis, application errors | Domain |
| `src/application/<concern>/` | Use cases, injected ports, write orchestration, plugin registry and events | Application and domain |
| `src/infrastructure/<concern>/` | Filesystem/process adapters, codecs, module loading, templates and framework renderers | Infrastructure, application and domain |
| `src/presentation/<concern>/` | CLI grammar, command definitions, input/output translation and invocation policy | Presentation, application and domain |
| `src/plugins/<id>/<layer>/` | A bundled core plugin's own layers, with the same inward rules | The plugin's inward layers plus kernel domain (and, above domain, kernel application) |
| `src/plugins/<id>/plugin.ts` | The core plugin's manifest and factory, wiring its layers to injected kernel ports | The plugin's four layers, kernel domain and application |
| `src/main.ts` | Composition root: construct adapters, bind services, register core plugins, run the invocation and clean up | All kernel layers and each core plugin's `plugin.ts` |
| `src/server-main.ts` | Detached server composition root: accept startup configuration and bind HTTP, snapshot and lifecycle adapters | Kernel infrastructure and domain contracts |
| `src/sdk.ts` | Explicit public type exports for plugin authors | Application and domain types only |

Domain and application use no Node or external package imports. Infrastructure owns runtime dependencies such as filesystem access, YAML parsing and child processes. Presentation uses Commander for CLI grammar and package metadata for discovery, but does not import infrastructure or instantiate its adapters. Simple text encoding belongs with input translation; document codecs stay behind application ports. Composition supplies concrete services instead of using a global service locator.

Command families own their handlers: document editing, generation and project/workspace operations each have a presentation concern, and core plugins such as `skills`, `ui` and `claude` own theirs. `src/presentation/cli/commands.ts` only assembles the kernel definitions in order; catalog commands own discovery responses. Every command declares its metadata (`src/application/plugins/command-metadata.ts`): scope, discovery, mutating, described options and arguments, per-action refinements, an optional output schema and its error codes. The pure `invocationPolicy` in `src/presentation/cli/invocation-policy.ts` derives workspace versus selected-project scope, plugin activation and explicit project selection from that metadata alone, with no command ids in code; `help` and `schema` (including each command's JSON Schema `inputSchema`) are generated from the same declaration. `src/main.ts` applies the policy when binding services, so routing rules have one owner and recovery/discovery commands do not depend on a stale project selection.

## Kernel and core plugins

The kernel keeps what every capability depends on: the CLI shell and command metadata, configuration, workspace and scope, the vault with its metadata cache and file manager, the event bus and the plugin host. It lives in `src/<layer>/<concern>/`. Features that only some workflows need ship as bundled **core plugins** in `src/plugins/<id>/`, each with its own `domain`, `application`, `infrastructure` and `presentation` folders and a `plugin.ts` entry, like Obsidian's core plugins. The bundle ships `templates` (shared Markdown templates, `make document` and the workflow pack), `scaffolds` (the TypeScript code generators, typed forms, plugin folders and the generated-project scaffold), `ui` (the component and interaction libraries, `make ui` and `make stories` with the seven framework renderers and Storybook), `data-sources` (REST and local-JSON definitions with `make data-source` adapters and fixtures), `claude` (native Claude Code agents, hooks and plugin assets, the installed CLI lifecycle and its `claude.lifecycle` service), `bases` (Bases queries), `skills` (the `skills` command and the bundled agent skills), `search` (text search), `links` (link reports), `vault-check` (the `vault` command: vault checks with severities and tag and property inventories), `agents` (docker-agent definitions and the Claude Code agents generated from them), `connector` and `connector-azure-devops` (backlog connectors), `backlog` (backlog-view compatible product backlogs and their sync engine), `webviews` (guarded publication of independent static prototypes) and `browser` (screenshots and illustrated tutorial playback). The Claude Code agent and hook validators are format contracts shared by `claude` and `agents`, so they stay pure kernel domain in `src/domain/claude/`; everything else about Claude lives in the plugin, and `agents` keeps working when `claude` is disabled. Kernel commands that need a feature reach it through a service, never an import: `setup` asks the registry for `templates.installer` and installs no templates (with a warning) when the plugin is disabled, and `project create`/`project component` keep scope management in the kernel but write the files of `scaffolds.projects`, failing with `PLUGIN_UNAVAILABLE` without it (`Registry.service` and `Registry.requireService`). `search`, `links` and `vault-check` read only through `context.workspace.files` and the metadata cache; `vault-check` validates `.base` files through the optional `bases.validation` service of `bases` and skips that rule without it, and it is not named `vault` because plugin ids name event namespaces and `vault.*` is the host's; `bases` additionally reads filesystem dates through the `fileDates` host port, because the repository port carries no dates, and `vault-check` reads file sizes for its `empty-file` rule through the same port, because the repository's `stat` reads and hashes the whole file. `agents` keeps docker-agent's semantic rules and the Claude mapping as pure functions in its domain (reusing the kernel's Claude agent validation from `src/domain/claude/`), validates the vendored JSON Schema with Ajv in its infrastructure, and reviews generated files with the kernel's `GenerationService` and review controls (`src/application/generation/`), the same pattern as the `ui` plugin's `make ui`, which `make` routes to like any generator. `ui` keeps its libraries at workspace scope through `context.environment`, parses definitions with the kernel document codec that the workspace carries, and reads its folders and default framework from `plugins.settings.ui`; interactions live in the same plugin because the renderers emit their handlers. `data-sources` follows the same pattern with `plugins.settings.data-sources`. Both keep their error codes in the kernel catalog, like `bases`, and their libraries' empty-state guidance comes from their own German strings through `localizedLibraryResult`, so the kernel localizer no longer special-cases their command ids. `backlog` evaluates its `.base` view through the `bases.query` service that `bases` provides, reads frontmatter and link resolution from the metadata cache, and writes guarded Workspace batches; a plugin whose required service has a disabled or unavailable provider stays registered but is unavailable, and its commands fail with `PLUGIN_UNAVAILABLE`. Backlog connectors follow the same pattern: the platform-neutral contract is a kernel port (`src/application/connectors/contract.ts`, with the neutral remote item model in `src/domain/connectors/`), the `connector` plugin owns connection profiles and the `connector.hub` service, platform connectors register with that hub when they load and reach the network only through the kernel `HttpClient` port (`host.http`, a `fetch` adapter in `src/infrastructure/connectors/`), and the backlog's sync engine uses the hub as an optional service: without an enabled, available provider `services.has('connector.hub')` is false and only `backlog sync` fails, so the backlog works without any connector.

Core plugins use the same contract as user plugins (`src/application/plugins/registry.ts`), with three differences: their manifest declares `core: true`, which only bundled plugins may; they may own bare command, generator and skill ids (service ids still start with `<id>.`); and they are enabled by default, with `plugins.disabled` turning one off so it contributes nothing. Their events stay in their own `<id>.*` namespace.

Layering stays inward. A core plugin depends only on kernel domain contracts and application ports, the internal plugin SDK, never on kernel infrastructure or presentation, and never on another plugin: plugins cooperate through declared services (`provides`/`requires`), which the registry resolves in dependency order (`src/application/plugins/plugin-services.ts`). Concrete adapters are still wired only by composition. `src/main.ts` lists the bundled plugins and calls `registerCorePlugins` with a `CorePluginHost` of kernel ports (`src/application/plugins/core-plugins.ts`); each plugin's `plugin.ts` exports a `CorePlugin` whose `create(host)` wires the plugin's own infrastructure and presentation to those ports, as a small composition root for one plugin, without I/O. Kernel code never imports `src/plugins/`, and `src/main.ts` imports only `plugin.ts` files. Architecture tests enforce these rules, including plugin-to-plugin and plugin-to-kernel-adapter imports, and `npm run check:structure` enforces the folder layout.

The registry also composes what plugins contribute to the kernel's catalogs: config sections validated against each plugin's JSON Schema under `plugins.settings.<id>` (`plugin-settings.ts`), whose canonical hash is the settings revision behind `onExternalSettingsChange`; localized strings and error catalog entries (`plugin-catalog.ts`), which the localizer merges after the kernel catalogs; and generators, which `make` routes to generically with the shared `GenerationService` for plan, check and drift. Host warnings and plugin state reasons are kernel messages with stable codes (`src/domain/shared/kernel-messages.ts`) rather than prose, so the presentation renders them in the response language like every other text the [localization policy](../reference/language.md#localization-policy) covers.

Within the `claude` plugin's presentation, agent, hook and authored-plugin asset handlers live in `agents.ts`, `hooks.ts` and `plugin-assets.ts`. `commands.ts` dispatches among those handlers and the installed lifecycle service. Argument parsing and text encoding are presentation responsibilities; the concrete codec and process implementations remain in infrastructure.

The workspace use case owns validation and post-commit notifications; command handlers do not publish fake `vault.*` events, and plugins cannot emit host-owned events at all. Plugin generators return write plans instead of writing directly. Core event delivery failures become warnings because persistence has already succeeded.

## Source placement and enforcement

Import concrete modules directly. There are no layer barrels or compatibility modules at old locations. The explicit type-only SDK is the public plugin contract; it does not expose host startup or adapter implementations. Packaged declarations are generated from that contract and the types it references.

Runtime implementation and generated-project assets have different roles even when both use TypeScript. The `scaffolds` core plugin's `src/plugins/scaffolds/infrastructure/projects.ts` produces project files from authored assets under `docs/templates/projects/`; reusable workflow documents live under `docs/templates/workflow/`. Those templates describe code or documents emitted into another project; they are not Forge domain models. Runnable examples live in `docs/examples/`. Infrastructure owns their loading and rendering, while framework-independent interaction selection and validation belong in domain. Installed, editable workspace templates remain in `bin/templates/`.

Build, release and quality programs live in the project's `scripts/`; versioned tooling and distribution policies live in its `configs/`. They are development inputs, separate from runtime adapters. Active user settings remain in the workspace `bin/config.json` and are preserved by builds. The committed workspace `bin` tree is the portable distribution, not an alternative source tree.

`configs/quality/source.json` selects the project's `src` as Forge's source inventory and `docs/examples` / `docs/templates` as additional authored-code roots; sibling managed projects live outside the project directory and are never scanned. `npm run check:structure` selects `--source-layout forge` to enforce layers and concern folders within that source root, and `src/plugins/<id>/plugin.ts` or `src/plugins/<id>/<layer>/` for core plugins; lint enforces file-size limits. Generated projects reuse the structure tool without that option or repository policy, retaining their default `src` inventory and intended flat domain/application output. Architecture tests inspect TypeScript syntax recursively across all four kernel layers and every core plugin, including side-effect imports, re-exports, type imports, dynamic imports, `require` and `import.meta.glob` patterns. A computed specifier cannot prove a boundary, so it is rejected everywhere except the user plugin loader (`src/infrastructure/plugins/loader.ts`, the only allowlisted module). A relative path may leave `src/` only from infrastructure and only into the approved asset roots `package.json`, `vitest.config.ts`, `configs/`, `docs/templates/`, `scripts/quality/` and `skills/` (kernel presentation may read `package.json`). They enforce the dependency table, reject plugin-to-plugin and plugin-to-kernel-adapter imports, keep `src/main.ts` on plugin factories, and separately reject runtime exports or outward dependencies in `src/sdk.ts`. Location checks and import checks serve different purposes: placing a file in a domain directory does not make an adapter dependency acceptable.

The event bus receives an `EventDeliveryScope` port rather than importing Node's asynchronous context machinery. Its `NodeEventScope` adapter uses `AsyncLocalStorage` to track active delivery ancestry. Each invocation creates a fresh scope and bus. This separates recursive notification chains from independent concurrent work, preserves the recursion bound across `await`, and stops completed callbacks from retaining a recursion budget for later notifications.

`src/application/plugins/host-events.ts` defines typed command, workspace, plugin and file notification contracts; the `claude` plugin defines its own `claude.*` contracts. Host phases describe application boundaries, not every syscall: direct repository calls and trusted plugin Node code remain outside workspace phases. Started and terminal operation records share an invocation-local ID and carry scope provenance. Command start precedes plugin activation; plugins can explicitly replay the bounded history to observe earlier registration/start records, then subscribe to future records through `onAny`. Replay is an in-memory snapshot, not persistent storage or an atomic catch-up subscription. Host failure summaries contain codes and status; raw input, error messages and native output remain outside those summaries. Awaited observer failures become warnings and do not replace the original result or undo commits.

Installed Claude execution is an application service of the `claude` core plugin behind its `ClaudeRuntime` port. The `claude` command and ordinary namespaced Forge plugin commands share `ClaudeLifecycle`, which plugins reach as the `claude.lifecycle` service. The plugin binds it on activation to the invocation's selected root, dry-run setting and its own event channel, and draws operation ids from the host's counter (the `operationId` host port); plugins supply native arguments and response parsing preferences without reconstructing CLI routing or importing infrastructure. Dry runs return redacted plans without constructing a process adapter. Real execution preserves native status and diagnostics, parses requested output even when Claude returns a nonzero status, and emits `claude.executed` only after receiving an exit status. Native process changes remain external operations rather than revision-guarded Workspace transactions.

## Kernel metadata cache

The metadata cache is the kernel's single index of what vault files reference. It follows Obsidian's `MetadataCache` so that features and, later, plugins can reason about a vault the way Obsidian does without running it. It has three parts:

| Part | Location | Responsibility |
| --- | --- | --- |
| Model and resolution | `src/domain/metadata/` | JSON-serializable `CachedMetadata` with `{line, col, offset}` positions, link text helpers, tag and alias rules, the indexed link resolver with `fileToLinktext`, and the stored snapshot's shape and reuse rules (`snapshot.ts`) |
| Index and port | `src/application/metadata/` | The `MetadataCache` read port, the `MetadataIndex` lifecycle port, the `MetadataParser` and `MetadataSnapshotStore` ports, and `VaultMetadata`, which builds `resolvedLinks`, `unresolvedLinks`, references and backlinks over a `FileRepository`, reusing stored parse results through `ParseResults` (`parse-results.ts`) |
| Parser and store | `src/infrastructure/metadata/` | `ObsidianMetadataParser`: Markdown through the document codec and remark/parse5, and Canvas file nodes; `NodeMetadataSnapshotStore`: the snapshot file in the workspace's `.forge/cache` |

The composition root creates one `VaultMetadata` per invocation over the selected scope's repository and exposes it as `context.metadata`. Nothing is read until a command calls `load()`. One vault rule (`vaultMember` in `src/application/metadata/vault-metadata.ts`) decides which paths a scope enumerates: no dot-prefixed segment and, for the workspace-root index, nothing below the workspace's own `bin/` distribution. The composition root marks the workspace-root index, so `search`, `links`, Bases and `app.vault` never treat the distribution as notes while direct reads still reach it; `vaultFiles()` lists the same paths without building the index. The first load lists those vault files, parses Markdown and Canvas files with bounded concurrency and resolves every reference through hash lookups, so a build is linear in vault size. Parse results and link resolution persist between invocations, as described next; backlinks and link counts are always recomputed.

### Persisted parse results

Parsing is the expensive part of a load, so `VaultMetadata` stores what it parsed and reuses it in the next invocation. The composition root gives the index a `MetadataSnapshotStore` and a key naming the Forge version, the parser version (`metadataParserVersion` in `src/infrastructure/metadata/parser.ts`, bumped whenever parse output changes) and the scope. The store keeps one file per scope in the workspace's `.forge/cache`: `metadata.v2.workspace.json` for the workspace root and `metadata.v2.project.<directory>.json` for each project (the number is the snapshot layout, `snapshotFormat`), with the project directory URL-encoded. Project trees therefore never contain cache files. A load works in three steps:

1. The store lists the scope's files and stamps each Markdown and Canvas file the index parses with its size, modification and status-change times in nanoseconds and inode (one synchronous `lstat` per such file; other files are listed by name only), taken before any content is read.
2. A Markdown or Canvas file whose stamp equals the stored one keeps its stored metadata without being read, unless it changed within two seconds before the listing that stored it (`racyWindowMs`, git's "racy clean" rule for files changed in the same timestamp tick as a read). Any other file is read and hashed. If a stored result exists for the same file kind and content revision, it is reused; this covers renamed and moved files and files that were only touched. Only new content is parsed.
3. Stored files missing from the listing are dropped. When the vault's paths and every note's aliases equal those the snapshot stored, each source whose content revision is unchanged takes its stored link resolutions; resolution depends only on the paths, the aliases and the source, so any other change resolves the affected sources again (all of them when a path or an alias changed). Backlinks and link counts are rebuilt from the resolutions, which needs no parsing.

The snapshot stores each position as an index into one list of six numbers per parse result instead of a nested object, which roughly halves its size and the time to read it back; a stored result that does not decode is parsed again.

After the command, the composition root calls `persist()`. It writes a new snapshot only when the index was loaded and something differs from the stored snapshot: a file was added, changed or removed, the vault's paths or aliases changed, or a re-read file's stamp can now be trusted. A file that stays inside the racy window, such as one with a timestamp in the future, is read on every load but does not rewrite an otherwise unchanged snapshot. A dry run reuses a stored snapshot but never writes one. Files re-indexed after a commit are stored without a stamp, so the next load reads them again but does not parse them. The store writes a temporary file and renames it over the snapshot. It works outside `Workspace` orchestration: no `vault.*` or `metadataCache.*` records, no writer lock and no revision guard, because the file is derived data. Concurrent invocations may overwrite each other's snapshot; that is safe because every stored file is validated again on the next load. The snapshot starts with a header line holding the document type, the identity of the running bundle (its size and modification time) and the SHA-256 of the JSON body. A truncated, corrupted, foreign, unreadable or other-build snapshot, or one for another key, is ignored and rebuilt, and the command never fails because of it. When the snapshot cannot be saved, the response carries a warning and the next command parses again. The store refuses to read or write through a symlinked `.forge` or `.forge/cache` folder.

The workspace root's `.forge/cache` is Forge's own state, like the writer lock: `list` and the vault rule leave it out, `vault check` never reports it, and its `.gitignore` keeps it out of Git. Deleting the folder is always safe and only makes the next command parse the vault again. An edit stays visible to the stamp check even when a tool restores the old modification time and size, because the status-change time (and, for editors that save by replacing the file, the inode) still changes. Only filesystems that do not maintain these times, or a file server clock more than two seconds behind, could hide an edit; delete the cache folder after changing files on such a filesystem.

`MetadataIndex.parseFile({path, bytes})` reuses a stored result for the same content as well, so `search` with tag, property or code filters parses only content that no earlier load has seen. It hashes `bytes` itself (the composition root injects the repository's SHA-256 revision function) instead of trusting a revision passed along with them, so planned or otherwise edited bytes never receive the metadata of the content they replace; hashing costs a fraction of parsing.

Link resolution has one implementation. It tries exact spellings with or without `.md`, then a single case-insensitive match, then for vault-style links a single case-insensitive path-suffix match, and finally a single note alias. Relative Markdown and HTML targets resolve from the source folder first and never match suffixes or aliases. When several files match equally well, the cache does not choose one. It records the link as unresolved, with reason `ambiguous` and the candidates in path order, and counts it in `unresolvedLinks`. Obsidian would choose the closest file instead; Forge reports the ambiguity rather than guess.

`update(changes)` and `invalidate(paths)` keep a loaded cache current after committed writes. They re-read and re-parse only the named files. When the set of paths or any alias changes, they re-resolve every source, which needs no parsing; otherwise they re-resolve only the changed files. The returned `{changed, deleted, resolved, prevCaches}` report names the paths that Obsidian's `metadataCache` `changed`, `deleted` and `resolve` events report, with each deleted file's previous metadata. An update before the first load returns `null` and does nothing, because the later load reads the current files.

`MetadataCacheEvents` (`src/application/metadata/cache-events.ts`) is the workspace's post-commit `CommitObserver`. After a batch commits and its `vault.*` records are published, it updates the index once for the batch and publishes `metadataCache.changed`, `metadataCache.deleted`, `metadataCache.resolve` and one `metadataCache.resolved`. A write never builds the index: metadataCache events are emitted for commits once the cache is loaded in the invocation, and commands that need link integrity (delete and move, links, Bases) load it. Observers are bound to one scope. When a project is selected, the project workspace feeds the project's index directly, and workspace-scope commits (such as the selection file or another project's files) reach it through `scopedCommitObserver` only for paths inside the project directory, made project-relative. Claude user-scope repositories have no observer.

Bases is the first consumer. The `bases` core plugin's `src/plugins/bases/infrastructure/index.ts` adapts cached frontmatter, references, tags and resolutions to the expression engine's file inputs and adds file sizes and dates. It keeps Bases' own rules: a link with an ambiguous path resolves to the closest candidate (`getClosestLinkpathDest`, as Obsidian opens it), links resolved only through an alias stay unresolved, and Canvas file nodes are not Bases links. A note the cache could not parse is indexed without properties, links or tags; both cases are reported as query `warnings` instead of failing the query. See [what the index understands](../reference/formats.md#metadata-index).

## Kernel file manager and the app facade

`move`, `rename` and `delete` are kernel operations because link integrity cuts across every feature. `src/domain/metadata/link-text.ts` holds the pure link-text rules: shortest wikilink text, relative and vault-absolute Markdown destinations, and offset edits. `src/application/vault/link-plan.ts` plans a move against the loaded metadata cache. It resolves every reference of every source before the move and again against a link index of the paths after the move, and rewrites only references whose text would stop resolving to the same (moved) file. `src/application/vault/file-manager.ts` (`FileManager`) turns that plan into one `Workspace.commit` batch: the rename plus a guarded write of every rewritten file, each guarded by the revision it was planned from. Deletion checks backlinks through the cache and commits a rename into `.trash` or a removal.

The repository port provides the transaction. `FileRepository.commit` (`src/infrastructure/workspace/batch.ts`) checks every rename, write and removal under the writer lock before changing anything, applies renames, then writes, then removals, fsyncs touched folders, and rolls back every applied step in reverse order when one fails. `Workspace.commit` publishes `vault.rename`, `vault.modify` and `vault.delete` records in that order, and the commit observer receives the renames, so the metadata cache moves entries instead of rebuilding them.

`apply` plans reuse this machinery instead of duplicating it. `src/application/documents/apply.ts` runs each operation in order through an ordinary `Workspace` and `FileManager` bound to `StagedFiles` (`src/application/documents/staged-files.ts`), an in-memory overlay of the scope's repository that records planned writes and moves, and to a fork of the metadata index over that overlay (`MetadataIndex.fork`), so every operation sees the paths, content and links of the ones before it while nothing is written. `src/application/documents/planned-batch.ts` then turns the planned state into one `Workspace.commit` batch: renames from each original path (whole folders where their files stayed together) and writes guarded by the revisions the plan started from. Dry runs, revision guards, rollback and `vault.*`/`metadataCache.*` records are therefore the batch's own; a batch cannot reuse a path it vacates, so such plans are refused. Section and block edits read headings and blocks with the metadata parser (`MetadataIndex.parseContent`) from the same bytes they edit.

`src/application/vault/app.ts` assembles the Obsidian-shaped `context.app` facade from the same scope's `Workspace`, metadata index, event channel and `FileManager`. It adds no second write path: every facade mutation is a guarded workspace call, so dry runs, revision guards and records are the ones the CLI produces. See [the app facade](../reference/plugins.md#the-app-facade).

## Declarative UI generation

`src/plugins/ui/domain/components/definition.ts` defines framework-neutral elements, scalar props, component references, child slots and Storybook metadata. `src/plugins/ui/domain/components/library.ts` owns graph invariants and reference selection; `src/plugins/ui/domain/components/syntax.ts` defines shared binding and element syntax. They reject duplicate IDs, missing references, cycles and invalid prop bindings before generation. `src/plugins/ui/application/components/library.ts` orchestrates library initialization, import/export and generation through injected codec/renderer ports. The Markdown codec and framework renderers live in the plugin's infrastructure; the plugin's `plugin.ts` wires them.

The shared library is workspace-scoped. Presentation translates selected-project output paths explicitly before passing plans to workspace orchestration. UI, stories and transferred Markdown use workspace collision checks, dry-run previews and post-commit events. UI regeneration accepts an explicit map of inspected destination revisions; import/export remains create-only. Definitions and their transitive references form a deterministic input graph: stable ordering and escaping produce repeatable bytes without timestamps or executing source content. Storybook extension modules remain ordinary target-project code and are imported by generated stories, never evaluated by the CLI.

The intermediate representation expresses elements, scalar props/state, bindings, composition and references to shared interaction definitions. `src/plugins/ui/domain/components/interactions.ts` owns framework-independent interaction values, state-use analysis and attachment validation against component state and element capabilities. Injected library ports supply definitions, and infrastructure renderers consume that analysis to emit executable handlers. Declared events/actions have a bounded portable contract; arbitrary framework state machines, asynchronous application workflows and framework-specific event systems remain application code. Framework-native extension modules let stories use executable Storybook APIs beyond JSON-compatible metadata. See [component contracts and limits](../reference/ui-components.md).

## Patterns adapted from obsidian-plugin-shell

The reference was inspected on 2026-10-07. This implementation adapts ideas rather than copying its runtime:

| Reference | Adaptation |
| --- | --- |
| [Plugin API](https://github.com/Luis85/obsidian-plugin-shell/blob/main/plugins/api.ts) | Explicit versioned manifest, command definitions, event descriptors and lifecycle context |
| [Plugin runtime](https://github.com/Luis85/obsidian-plugin-shell/blob/main/plugins/runtime.ts) | Atomic contribution validation, duplicate rejection, owned namespaces, `onload` and reverse `onunload` cleanup |
| [Event bus design](https://github.com/Luis85/obsidian-plugin-shell/blob/main/docs/architecture/EVENT-BUS.md) | Runtime payload checks, notification isolation, scoped subscriptions and events after committed changes |
| [Document generation](https://github.com/Luis85/obsidian-plugin-shell/blob/main/docs/development/GENERATOR-DECLARATIVE-ACTIONS.md) | Validated inputs, explicit plans and stale-write guards through a single storage owner |

The standalone environment changes several choices: shared `bin/plugins` directories use Obsidian-inspired manifests and ESM/CommonJS entry points without a core rebuild; Node implements storage; no GUI, host bridge, Vue or Obsidian API is needed; listener delivery is explicitly awaited and ordered for one CLI invocation. Established libraries own CLI grammar, configuration validation, Markdown parsing, YAML and date formatting. DDD is applied to meaningful invariants and vocabulary rather than introducing aggregate/repository layers with no behavior.

## Intentional limits

The event bus is ephemeral, not a durable queue or event-sourced store. The optional localhost server is a detached process configured through startup IPC; it polls read-only CLI snapshots and does not watch files or persist event history. Plugin code is trusted Node code, not sandboxed. Each replaced file and changed directory entry is fsynced before a write reports success, and a multi-file write rolls back reported errors, but a batch cannot promise crash atomicity. An external editor does not honor the CLI lock. Forge breaks a lock only when its holder provably no longer runs on this host; a lock from another host, container or boot is reported, never removed. Scaffolds encode useful boundaries but cannot invent a project's business rules or prove its quality. Skills guide the agent to establish acceptance criteria and verify behavior after generation.


## Localhost server and developer admin

The CLI's `server` commands use the `ServerController` application port. `main.ts` injects the Node controller; the separate `server-main.ts` entry composes the detached HTTP process. The server binds only `127.0.0.1`, authenticates API requests with a per-instance capability, validates Host and Origin, and serves installed static webviews from manifests under `bin/webviews/<id>/`. The server does not import a webview's source or framework. See [the server contract](../reference/server.md).

The independent `src/forge-admin` project builds Vue and Nuxt UI into static assets. Its HTTP contract is versioned JSON: workspace context, projects, plugin state, capability counts and runtime health. Fixed read-only CLI discovery commands supply snapshots; there is no arbitrary command execution API or browser configuration editor. Browser refreshes share a short-lived snapshot cache. Each project owns its toolchain and tests; the maintained distribution combines the two prebuilt artifacts.

The `scaffolds` plugin supplies independent Vue/Nuxt UI starter projects through `project create --type webview`. The `webviews` plugin owns inspection and publication of their compiled `dist` assets through `context.environment.commit`; it neither runs package scripts nor imports the admin project. Check-only batch guards verify the source and installed folder revisions under the writer lock before applying asset writes and obsolete-file removals. Custom views remain user-owned and are excluded from Forge's release manifest. The `forge-webviews` skill connects generation, project-local checks, publication and CLI server lifecycle into a repeatable prototyping workflow.

Server lifecycle state is derived local data under `.forge`, separate from document mutations. A private state file holds the instance identity and token; startup and shutdown use a dedicated lock. The controller verifies authenticated identity before requesting shutdown and never kills a PID taken from stale state. Dry runs do not start processes or write lifecycle state. Playwright tests start and stop the actual portable CLI in isolated temporary workspaces.

## Browser evidence and tutorial generation

The `browser` plugin keeps input validation, tutorial plans and guarded output publication in its own domain/application layers. Its Playwright adapter implements a plugin-local runtime port; the composition root supplies the portable distribution path. Playwright Core is shipped intact under `bin/browser-runtime/playwright-core` because its browser registry and runtime assets use relative paths. Chromium is a separate machine-level dependency, installed explicitly with `browser install` or selected through an executable path. Capture commands never download a browser implicitly.

Screenshots are captured into memory and written through the selected workspace with revision guards. Tutorial source is an explicit versioned JSON plan, optionally embedded in Markdown or a Canvas text node. The agent skill translates prose or diagrams into that reviewable plan; the CLI does not infer interactions. Playback uses an isolated browser context and completes before one guarded batch publishes `index.md`, screenshots and `flow.json`. Failed playback leaves existing local output intact; browser interactions may already have changed the application being documented. Dry runs neither launch browsers nor visit pages.
