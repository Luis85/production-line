# Why UI generation is declarative

[Documentation](../index.md) · Explanation

The Forge treats a component definition as data: an element tree, scalar props and local state, references to other components, a default child slot, and declarative event/action attachments. This small shared model can be rendered into HTML, HTMX, vanilla JavaScript, Vue, Svelte, React or Angular without asking a model to infer an implementation on each run.

## Reproducibility has explicit inputs

The same component and interaction definition graphs, target framework and output paths produce the same generated bytes. Stable ordering, explicit escaping and the absence of timestamps make generated changes reviewable. Paths are inputs because imports between components, stories and native extension modules are relative. A change of source, framework or path can legitimately change the output.

Library validation precedes generation. Unknown references, cycles, duplicate IDs, invalid bindings and type mismatches are rejected before write planning. Generation includes the selected component's transitive dependencies so those references have concrete target files. The output is a write plan committed by the same workspace owner as ordinary file edits.

## Shared definitions, native application behavior

The declarative model captures structure that has a clear representation across the supported targets. It does not attempt to translate arbitrary React state, Vue directives, Svelte expressions or Angular dependency injection into other frameworks. A shared [interaction contract](../reference/interactions.md) covers named browser events, typed local state changes, safe navigation and native custom events. Renderers express that bounded behavior through each target's lifecycle. Server endpoints, application routing, asynchronous workflows and styling remain consuming-application responsibilities.

The initial catalog provides semantic elements and composition primitives. A `modal` or `accordion` definition provides markup; it does not establish a complete interaction or accessibility implementation. Applications must implement and test focus management, keyboard behavior and other domain-specific behavior they require. SVG/MathML namespaces currently require image assets or native application code.

Storybook follows the same boundary. JSON-compatible metadata belongs in Markdown; executable decorators, loaders, interaction tests and framework providers belong in native extension modules. The CLI imports no extension code during generation. Storybook executes those modules through its normal renderer and addon system, and that downstream behavior has its own dependencies and determinism.

## Regeneration respects ownership

Generation is create-only unless the caller supplies current revisions for existing outputs. A revision map identifies exactly which reviewed versions may be replaced. It does not decide how to merge handwritten edits with regenerated code; that reconciliation remains the author's responsibility. Dry runs validate a snapshot and expose planned text, but do not lock or reserve future destinations.

This separation makes the result predictable without pretending that generated boilerplate is a production application. Validate the definitions, review the plan, then compile and exercise the output with the target project's tooling.
