# Stage prompts: Team Purchase Approvals

Copy one prompt at a time and attach its named input files. Work in the consuming product repository, not the Forge source repository. Replace project-specific paths, owners and provider details with known values. These prompts produce bounded artifacts or implementation work; they do not authorize contacting people, purchasing services or deploying to an unspecified environment.

Use this instruction with every stage:

> Read AGENTS.md and the actual repository scripts first. Preserve requirement/use-case/test IDs and existing decisions. Label evidence as observed, assumed, proposed or not run, and cite its source. Never invent research, test results or deployment status. Read `node bin/forge.js config --json`, `schema --json` and `project current --json` from the workspace when CLI work is needed; verify context and check both exit status and JSON `ok`. Preview writes, inspect conflicts and preserve concurrent work. Continue authorized work autonomously. Ask only for missing decisions that block dependent work; use existing authorization when it already covers an action. End with changed artifacts, verification evidence and unresolved decisions, not a duplicate of every document.

## 1. Refine the opportunity and PRD

> Inputs: 01-opportunity.md, 02-prd.md, and any supplied research/constraints. Check whether the problem and audience are supported by evidence. Identify the three highest-impact unknowns and propose the cheapest ethical validation for each. Refine the PRD in place: measurable outcomes with explicit baselines, scope/non-goals, actors, limits, acceptance criteria, accessibility, data handling and owners. Keep illustrative targets labeled as proposed. Output the revised two files and a short decision table linking each changed REQ/OUT ID to its rationale. Do not turn an unvalidated assumption into a product commitment. The product owner must decide scope and success measures before dependent implementation; continue independent discovery preparation meanwhile.

## 2. Design the journey and interface

> Inputs: approved portions of 02-prd.md, 03-use-case.md, 04-build-specification.md and components/*.md. Check every requirement against primary, alternative and failure flows. Refine UC-01 and the UI-state table; specify keyboard/focus behavior, mobile/zoom layout and recovery from uncertain network outcomes. Describe necessary component composition and identify behavior that must remain native application code. Update the actual Markdown definitions using the documented strict schema, then run `components validate --library docs/examples/idea-to-production/components`. Preview `make ui approval-page --library docs/examples/idea-to-production/components --project purchase-approvals --framework react --stories --dry-run` only after verifying that project exists. Output changed design/spec files, generated-path preview and unresolved interaction decisions. Seek a product/design decision on material scope tradeoffs; do not call a static fixture a working flow.

## 3. Break down implementation

> Inputs: agreed PRD, use case, build spec, ADRs and current target-project source. Refine 05-delivery-plan.md into small vertical slices, each with dependencies, owned files, requirement IDs, acceptance tests and a clear done condition. Identify integration contracts before parallel work. If subagents are authorized, assign disjoint files and have one coordinator integrate shared contracts and project context. Flag prerequisites such as identity provider, database, framework/Storybook setup and deployment owner. Output only the updated plan/test map and unresolved dependency decisions. Do not replace meaningful integration tests with tests that merely compare generated strings.

## 4. Implement one slice

> Inputs: one chosen slice ID from 05-delivery-plan.md, its linked requirements/specification and the target project's AGENTS.md. Verify the selected project before mutation. Define the slice's acceptance examples, inspect existing code and implement the smallest complete behavior across necessary boundaries. Use Forge scaffolds only when they help: `project component purchase-approvals PurchaseRequest --kind domain --dry-run` or `make ui ... --dry-run`, then execute the inspected command. Validate the `sources` library before `make data-source`; configure adapter/test-data output paths and inject runtime authentication or the local JSON loader. Generated classes need real invariants; generated UI needs native state, authorization and integration. Generated adapters validate transport shapes, not purchase policy or authorization. Keep handwritten feature code outside generated directories. Use guarded revision-map regeneration or a new comparison directory when outputs already exist. Run relevant tests and project checks; fix causes of failures. Output a reviewable diff summary mapped to REQ/T IDs, commands actually run and remaining limits. Do not silently implement another slice or claim a deployment.

## 5. Test and independently review

> Inputs: implementation diff, PRD/use case, traceability table and current test output. Review product behavior, API/domain invariants, cross-organization access, concurrency, failure recovery, accessibility, responsive layout, performance and operator experience. Look for gaps between generated presentation and real behavior. Exercise T-01–08 at appropriate boundaries; use an independent reviewer if available and authorized. Run the target project's actual configured checks, including Storybook/browser checks when installed. Record pass/fail/not-run with commit and evidence; keep manual checks explicitly manual. Fix actionable issues, rerun affected checks and update the release ledger. Output prioritized findings with concrete trigger/impact plus evidence, or say no actionable findings within the tested scope. Never infer production readiness from a green Forge repository check alone.

## 6. Prepare and execute the authorized release

> Inputs: reviewed commit/artifact, completed release ledger, real provider runbook, target environment and existing authorization. Verify REL-01–05, exact build/migration/deploy/rollback commands, artifact identity, secrets references and the incident owner. Rehearse on staging with synthetic data and capture results. The Forge has no deploy command: use only the chosen provider's verified commands. If production authorization is missing, finish the concrete release plan and artifact first, then request the specific authorization required by the team's policy; otherwise proceed within existing authorization. Do not deploy while a required evidence/owner/provider value is unresolved. After an authorized deployment, verify health, access control, one idempotent decision and audit consistency; stop/rollback according to the runbook on failure. Output environment, version, exact executed commands, evidence and active limits without exposing credentials.

## 7. Learn and refine

> Inputs: pilot observations, incident/accessibility findings, baseline, actual OUT-01–03 measurements and support effort. Separate measured changes from hypotheses and explain sample-size/data-quality limits. Update the opportunity/PRD and add only evidence-backed follow-up slices. Preserve history of rejected assumptions and link each proposed improvement to an outcome or finding. Output one short review with continue/change/stop options, the product owner's recorded decision if provided, and a prioritized next plan. Do not send surveys, messages or export user data without authorization.
