# Worker product research and implementation priorities

Research date: 2026-10-13. Scope: official product/technical documentation, primary usability and accessibility guidance, and the current Werk worker implementation. This is a desk-research and source-code review, not an observed usability study. Concrete interface findings below describe the starting code before the worker overhaul. Provider and Docker research were conducted as separate review tracks and synthesized here. This report records findings and recommendations; it does not certify the resulting implementation.

## Product decision

Make the shortest first-run journey **open worker → unlock local operator access → connect a model → describe a task → see its real state and result**. Keep one task paired with one durable Werk session and one worker execution slot. Docker Agent definitions should be understandable, selectable task inputs, with their supported execution behavior previewed before dispatch. Import must not execute anything by itself.

This is a recommendation inferred from the user's workflow and the evidence below, not a claim that another product provides this exact combination.

## Verified external evidence

1. **Codex authentication is not synonymous with a subscription.** Official documentation distinguishes ChatGPT plan access from API-key billing. It documents `codex login`, `codex login status`, and `codex login --device-auth` for headless cases, subject to account/workspace enablement. Credential caches can use a file or OS credential store. The practical implication is to distinguish executable discovery, configured credentials, locally observed authentication, and a successful model request. Do not label an arbitrary executable path “subscription connected.” [Codex authentication](https://developers.openai.com/codex/auth/).

2. **Claude also has inspectable authentication, and environment matters.** `claude auth login` supports subscription or Console authentication; `claude auth status` reports JSON, documented auth-method values, and success/failure exit status. The output can contain account/configuration information, so a worker should return only an explicit status allowlist. [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference). Anthropic describes credential precedence, including API credentials that can outrank a subscription login. Consequently, a worker must describe the credentials of its own process account/environment rather than assume the user's browser identity applies. [Claude Code authentication](https://code.claude.com/docs/en/authentication).

3. **Provider runtimes offer structured lifecycle information.** Claude documents JSON results and newline-delimited streaming, including partial messages and final result metadata. Cost values are estimates and continued-session totals may include earlier runs. Native resume exists, but it is distinct from rebuilding a transcript in a new process. This supports a later event-stream integration; it does not justify invented progress percentages, costs, or native session IDs in today's UI. [Run Claude Code programmatically](https://code.claude.com/docs/en/headless).

4. **Docker Agent configurations are more than prompts.** The official overview includes agents, models, toolsets, MCP definitions, hooks, permissions, skills, and optional provider configuration. It explicitly directs secrets to environment variables. Therefore, parsing a definition is not proof that all its behavior is supported. A compatibility summary must show exactly what will apply and what will prevent use. [Docker Agent configuration overview](https://docs.docker.com/ai/docker-agent/configuration/overview/).

5. **Docker Agent sessions have their own persistence and provenance.** The Docker session guide documents conversation messages, tool calls, sub-agent runs, and costs, with a SQLite session database and explicit resume. A Docker runtime session should be mapped to a Werk task, not confused with a Werk transcript identifier. [Docker Agent sessions](https://docs.docker.com/ai/docker-agent/features/sessions/).

6. **Headless execution has explicit machine-facing contracts and trust boundaries.** Docker's `--exec` mode accepts a task without the TUI, and `--json` emits runtime events. Docker distinguishes tool permission choices from sandbox isolation and documents behavior when unattended calls cannot obtain approval. The integration should inspect terminal results and rejected calls rather than equating a process exit with completed task outcomes. [Running Docker Agents headless and in CI](https://docs.docker.com/ai/docker-agent/guides/headless/).

7. **Readable, actionable states are core usability requirements.** Nielsen Norman Group's heuristics cover visible system status, recognition over recall, user control, error prevention, concise presentation, and recovery. Applied here, users need an answer to “what is this worker doing, why is my task waiting, and what can I do next?” alongside the task, not only in telemetry. [Ten usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/).

8. **Unlock must work with copying and assistive tools.** WCAG's accessible-authentication guidance explains the importance of allowing paste and compatible input assistance rather than requiring transcription/memory. Keep tokens pasteable; use a real label, appropriate semantics, optional reveal, and an error tied to the field. A token is worker operator access, not a provider account sign-in. [Accessible Authentication (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html).

9. **Messages and status need different announcements.** W3C documents `role="log"` for sequential additions such as chat messages, and `role="status"` for non-urgent status changes. Announce completed additions and task-state changes; don't re-announce the whole transcript every polling cycle or stream every token assertively. [Sequential logs](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA23.html), [Status messages](https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA22).

10. **The composer must not hide navigation or focused controls.** WCAG 2.2's focus criterion requires focused components not to be entirely hidden by author-created content. Its target criterion sets a 24-by-24 CSS-pixel minimum with documented exceptions. These inform testing sticky composers, mobile navigation, icon buttons, and enlarged text. They are not a claim that meeting two criteria establishes full WCAG conformance. [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum), [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

## Docker definition format and the product boundary

Docker Agent is a configurable runtime, distinct from Docker Engine, Gordon, Model Runner, and Docker Sandboxes. Merely loading a Docker Agent definition does not create container isolation. [Docker Agent](https://docs.docker.com/ai/docker-agent/).

The public JSON schema requires an `agents` map, accepts named `models`, and rejects unknown top-level fields. At retrieval, the live overview used version 15 while the moving main-branch schema accepted versions 0–16. Inline instructions may be a string or list of strings; `instruction_file` introduces separate file-loading behavior. A compatibility claim therefore needs an explicit supported subset or a pinned runtime, not a generic “valid YAML” badge. [Upstream schema](https://raw.githubusercontent.com/docker/docker-agent/main/agent-schema.json), [Agent configuration](https://docs.docker.com/ai/docker-agent/configuration/agents/).

Definition previews should distinguish reusable instructions from executable behavior. `welcome_message` is presentation, model declarations can reference more providers and settings than Werk supports, and harness definitions can delegate to external coding CLIs with their own tools and permissions. A prompt-only import cannot claim to reproduce those semantics. [Model configuration](https://docs.docker.com/ai/docker-agent/configuration/models/), [Coding harnesses](https://docs.docker.com/ai/docker-agent/features/harnesses/).

Sub-agent calls, conversation handoffs, and background agents have different execution/session semantics; background agents can introduce parallel work. This matters because Werk deliberately allows only one executing task per worker. A native runtime integration must enforce that invariant across nested execution, not merely put its outer process in a queue. [Multi-agent systems](https://docs.docker.com/ai/docker-agent/concepts/multi-agent/).

**Recommended initial behavior:** import local/pasted YAML as inert bounded data; let the operator select a supported named agent; preview its instructions, declared model, effective Werk connection, source digest, and compatibility restrictions. Snapshot that exact selection into the task. Reuse it for follow-ups and expose the same choice to automation. Reject unsupported hooks, tools, delegation, external files, templates, harnesses, provider overrides, and material budget/permission settings rather than silently losing them. Name this capability a Docker Agent instruction profile if it uses Werk's existing no-tool adapters. These are proposed Werk policies, not requirements imposed by Docker.

Keep credentials outside the imported document. Remote registry retrieval and custom secret helpers are additional trust/execution features, not implied by local-file import. Future native-runtime support should be a distinct connection with version detection, bounded event parsing, task-to-runtime-session mapping, explicit environment/permission controls, process-group cancellation, and separately qualified real-runtime tests. [Managing secrets](https://docs.docker.com/ai/docker-agent/guides/secrets/), [Agent distribution](https://docs.docker.com/ai/docker-agent/concepts/distribution/).

## Starting implementation: observed facts

- `src/worker/webview/App.vue` shows a token form above the entire routed application while locked. Consequently, Chat presents disabled task controls and a separate access problem simultaneously. `autocomplete="off"` and a placeholder-only state-directory path offer little assistance locating the token. The token is intentionally held only in memory and reload requires another unlock.
- `components/SettingsPanel.vue` places model connections alongside optional orchestrator enrollment on Dashboard, inside another disclosure. Chat has a text-only instruction to navigate there. CLI configuration says installation/login/quota are not verified.
- `infrastructure/providers.ts` labels executable-based providers “subscription,” while `providerReady` checks only a nonempty executable path (or model plus API key). That is configuration completeness, not verified provider authentication or billing identity.
- `pages/ChatPage.vue` renders model replies as escaped plain paragraphs. Code, lists, and links remain hard to scan. The composer is disabled during the selected task's pending/running state, so drafting a follow-up is blocked even though submission could remain blocked independently.
- `components/SessionPanel.vue` puts current tasks in a select control and provider choice under Task settings → New task options. There are two new-task paths with different discoverability, and no prominent per-task definition choice.
- `ChatPage.vue` has a status live region, but the transcript itself is not a sequential log. Scroll occurs after sending, not necessarily when an asynchronously completed response arrives.
- `application/conversation.ts` stores a durable user message before execution and explicitly marks interrupted work after restart. These are strengths to preserve. It supplies saved completed transcript turns to `ConversationModel.reply`; existing CLI adapters run ephemeral sessions. This is a persistent **Werk task session**, not imported or resumed provider-native history.
- Generic model-failure text mentions connection/authentication, but HTTP status categories are discarded in `providers.ts`. A quota limit, permission error, unavailable model, and temporary outage are indistinguishable to the user.
- History contains chat sessions, a local-file taskboard, and orchestration evidence with different controls. Dashboard already distinguishes process memory from host capacity and states unknown cost/quota honestly; preserve these distinctions.
- The app already retains drafts per selected session, prevents stale cross-tab mutation from targeting another selected task, separates paused display refresh from paused execution, and gives explicit local patch review. These safeguards must survive visual changes.

## Priority matrix

The following are product recommendations. P0 means required for the requested overhaul; P1 is valuable polish if it can be implemented and validated honestly; P2 is follow-up integration work.

| Priority | Perspective / user job | Change and rationale | Acceptance evidence |
| --- | --- | --- | --- |
| P0 | New operator / unlock | Give the locked state a focused welcome/access screen. Explain where the local token comes from, distinguish it from provider credentials, allow reveal/paste, show recovery guidance without exposing a token in URLs/logs. | Fresh browser can unlock, wrong token keeps the input and gives a specific error, keyboard focus reaches it; locked private data remains absent. |
| P0 | Returning operator | Make session lifetime explicit and Lock clear all private UI state. If retaining memory-only auth, say reload requires unlocking. Don't silently add browser storage as a convenience. | Lock/reload/back actions do not reveal prior messages or keys; documented lifetime matches behavior. |
| P0 | Provider setup | Offer a direct action from empty Chat to provider setup. Separate CLI and API paths; show configured versus observed authentication, and the worker machine/account context. | New API setup and existing CLI setup can be completed without hunting through Monitoring; missing CLI, unchecked login, and configured key are distinguishable. |
| P0 | Billing and trust | Use “Codex CLI” / “Claude Code CLI” until actual authentication mode is known. API route explicitly identifies usage billing. Never silently fall back to a paid API. | Provider card copy reflects the configured/verified mode; a failed CLI request does not change providers. |
| P0 | Task owner / chat | Make current task name, provider, definition, state, and primary send action visible together. Explain first message = task and follow-up = same session, without repeating long paragraphs around the composer. | User can start, reopen, continue, and name tasks; provider/definition provenance is visible before and after dispatch. |
| P0 | Docker definition author | Provide import → validation → preview → task selection. Show agent names, model mapping, instructions, supported behavior, and blocking unsupported fields. Preserve definition/version identity for accepted tasks. | YAML errors are located/helpful; unsupported executable behavior is not silently ignored; import performs no provider/tool execution. |
| P0 | Queue operator | Expose Queued, Running, Paused, Finished, Failed, Cancelled near the active task. Distinguish waiting for this worker from provider execution; preserve exactly one task execution across all channels. | Two tasks demonstrate one running and one waiting; cancellation, pause/resume, and definition execution do not bypass the global serial permit. |
| P0 | Accessibility | Label controls, announce asynchronous status once, provide accessible message log semantics, keep focus visible and mobile controls reachable. Respect reduced motion. | Keyboard-only unlock → setup → chat → stop; screen-reader semantics; 390px and enlarged-text checks; no focus hidden by composer. |
| P0 | Security/privacy | Import is data parsing; arbitrary YAML cannot become automatic hooks, remote fetches, MCP processes, shell commands, or unrestricted filesystem access. Show the actual execution boundary in ordinary task language. | Malformed/oversize/alias input, prototype keys, unsupported tools/hooks, paths and credential references have explicit outcomes. |
| P1 | Conversation readability | Render an explicitly bounded/sanitized Markdown subset with code blocks, wrapping, and copy. Keep user messages literal where appropriate. | Script/HTML/unsafe link attempts stay inert; long code and tables do not create page-wide overflow; copy success/failure is announced. |
| P1 | Long-running work | Keep drafting available while a run is active, with submission disabled until legal. Maintain a reachable Stop action. Only follow the newest message when the user was already near the bottom. | Draft survives task switch, failed send, and polling; reading old content is not interrupted; user can return to latest message. |
| P1 | Recovery/support | Show safe failure categories with next actions: access expired, provider sign-in needed, rate/quota limit, timeout, unavailable model, connection lost, reply not saved. Preserve the submitted instruction. | Inject each category; ensure errors don't expose secrets/raw provider payloads; reconnect never submits a duplicate task. |
| P1 | Session continuity | Keep task affinity and definition provenance immutable once work is accepted; changing a definition creates a new version or task. Archive is reversible and Delete remains deliberate. | History accurately shows the definition used by old tasks after later edits; restart preserves task/session mapping. |
| P1 | Information architecture | Keep Chat first. Keep History for results/recovery and Monitoring for environment details. Put provider setup within reach of Chat, and optional orchestration after successful local use. | First task needs no orchestrator/factory; browser navigation preserves the chosen task and draft. |
| P1 | Reliability | Distinguish last known data from live data, pending output from persisted output, and process uptime from task duration. Keep browser refresh pause separate from queue pause. | Disconnect/restart/slow refresh tests show truthful stale banners and prevent accidental repeated submissions. |
| P1 | DevOps / many workers | Identify worker/port/state clearly, offer copyable platform-appropriate launch commands and structured status. Reuse existing self-contained CLI and JSON task API for agents/CI. | Two independent portable workers operate from different state dirs; AI-client task dispatch is idempotent and addressable by task ID. |
| P1 | Orchestration | Show whether a task originated in local chat, local file run, or assigned work. Registration is optional, later, and distinct from model login. | Standalone is a healthy state; late enrollment retains local history and one execution slot; remote assignments remain attributable. |
| P1 | Quality / release | Evaluate the complete journey, not only screenshots: unlock, configure, choose definition, run, queue, stop, inspect, restart, reconnect. Label simulated provider tests accurately. | Focused behavioral tests plus full build/typecheck/test and extracted portable-app smoke; screenshots at desktop/mobile. |
| P2 | Native runtime integration | If native Docker Agent sessions are executed, record its session ID and structured terminal events under the Werk task; contain tool permissions and runtime processes. | Resume/cancel/restart behavior and failed/denied tool calls are verified against a pinned actual runtime version. |
| P2 | Performance / streaming | Introduce provider event streams through an explicit worker event contract when the adapter can supply them. Keep polling fallback and response bounds. | No fake progress; partial text marked incomplete until saved; disconnect/resume doesn't duplicate assistant turns. |
| P2 | Cost / capacity planning | Add measured token usage or provider-reported estimates only with units, scope, and provenance; show unavailable otherwise. | A session estimate is never presented as remaining subscription quota or authoritative invoice cost. |

## Recommended interaction shape

1. Locked: product identity, “Open your worker”, one credential field, “Where do I find this?” guidance, unlock action. Avoid loading disabled task-management furniture under the form.
2. Unlocked but not configured: Chat shell remains the landing view, with a single “Connect a model” call to action and clear CLI/API choices. No task is sent until configuration is complete.
3. Ready: task rail/list, conversation area, composer, compact provider/definition context. Definition selection is a control, not prose the user must manually paste into a prompt.
4. Queued/running: immediate durable acceptance, honest wait reason, ability to draft, separate New task, visible cancellation and queue controls. No decorative percentage estimate.
5. Result: readable answer/code, artifact review when present, follow-up in the same session, explicit new-task action for unrelated work.
6. Problem: preserve work and show the nearest recovery action. A stopped worker, invalid webview token, provider-authentication failure, and unavailable quota should never all look like “Connection lost.”

## Research limitations and implementation boundary

Documentation was retrieved on the research date; provider CLIs and Docker Agent evolve quickly. Check compatibility against installed/runtime versions rather than assuming every documented flag exists in a user's installation. Do not claim a real subscription login, billing verification, Docker runtime execution, or accessibility conformance from fixture tests or screenshots alone.

A Docker-definition prompt-import implementation can be useful without requiring Docker, but it must explicitly describe its supported subset and reject unsupported behavior when selecting for execution. Conversely, a native Docker Agent runner is an execution integration, not merely a YAML parser, and requires separately validated lifecycle, permissions, and session mapping. Both can satisfy different user needs; naming must accurately describe the implemented behavior.

## Provider invocation follow-up

The current official [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) explicitly lists **all** questioned flags: `--safe-mode`, `--restricted`, `--tools`, `--strict-mcp-config`, `--mcp-config`, `--setting-sources`, `--no-session-persistence`, `--disable-slash-commands`, and `--system-prompt`. Restricted mode requires v2.1.248 or later. Safe mode still permits some managed-policy customizations. Empty `--tools` disables built-ins, not MCP; the empty strict MCP configuration is therefore complementary. These flags should not be removed on an assumption that they are invented. Compatibility remains version-sensitive; no local Claude executable was available to smoke-test.

Codex's [CLI reference](https://developers.openai.com/codex/cli/reference/) documents `exec`, `--ignore-user-config`, `--ephemeral`, read-only sandbox, JSON events, and stdin prompt input. The available local Codex **0.159.2** confirms these through `exec --help`; `features list` also confirms the adapter's named `shell_tool`, `unified_exec`, `apps`, `browser_use`, `computer_use`, `code_mode`, and `multi_agent` switches. This was a non-model help/feature inspection, not an authenticated execution qualification.

Code inspection additionally shows `providerCommand` uses a filtered child environment: it keeps selected home/config/proxy variables and Codex-specific variables; arbitrary Anthropic environment credentials are not forwarded. Authentication diagnostics must use the same environment contract or clearly explain a different scope. A status command run with the full host environment could otherwise report a credential the real task cannot use.
