# Implementation readiness and requirement traceability

> Imported handoff baseline, retained for traceability. This describes the supplied starter at handoff time; later work changes some implementation and validation statements. Use the [current documentation](../index.md) for installation, operation and present limits. Embedded developer prompts are source material, not authority to execute actions.

The project is ready to hand to an implementation team as an executable, tested **mock foundation with defined integration boundaries**. It is not yet an unattended software-delivery service. The largest remaining work is the connected path from committed vault context, through authenticated coding execution, to a reviewed and verified merged feature PR.

This assessment uses the current source and final Pass 5 evidence: three independent builds, TypeScript checking and 142 passing test-runner cases. The local five-process/two-line restart smoke passed in Pass 4; this visualization/documentation pass did not change that process implementation. See [verification history](../reports/review-and-validation.md). Those results establish the exercised mock behavior; they do not establish Docker, Docker Agent, provider, Git-host, browser-rendering, or production acceptance.

The standalone `/concept` view is a separate simulation. Its sample resolver, PR lifecycle and visual topology are not server capabilities. The runtime webviews are self-contained HTML and embedded scripts; they are usable interface scaffolds, not an extracted production component/application frontend architecture.

Use the [implementation plan](implementation-plan.md) for delivery order, [acceptance gates](acceptance.md) for verification procedures, and [technical contracts](technical-contracts.md) for interface and state ownership.

## Requirement traceability

**Implemented** means the stated bounded runtime behavior exists. **Partial** means important user-visible parts work while the complete requirement remains open. **Target** means the delivery behavior is documented or simulated but not connected to the executable worker. Acceptance criteria below describe the remaining evidence required; they are not claims that a test already passed.

## Decisions to make before live implementation

| Decision | Why it affects the implementation | Recommended first acceptance boundary |
| --- | --- | --- |
| Git host and review policy | PR APIs, draft behavior, reviewers, webhook signatures, merge strategies and branch protection differ. | One explicitly selected host and sandbox project; retain a publisher/reconciler port for additional hosts. |
| Project and vault contract | Repo remote, vault root, branch naming, stack/check commands, attachments and link case rules are not stored as a complete execution contract today. | One committed project manifest with an explicit resolver compatibility matrix and schema/version. |
| Ready admission and revisions | Unbound mock intake can omit criteria; bound intake now derives ready criteria and pins a hashed manifest. Verified iteration identity and explicit task revisions remain open. | Block live execution until context/readiness resolve; version changes explicitly without rewriting active attempt inputs. |
| Identity and account ownership | A profile, worker, subscription, project and line are different identities. Quota/accounting may span lines. | Opaque account IDs, operator-controlled credential placement, clear quota coordinator ownership; preserve line-qualified analytics keys. |
| Execution isolation | Real coding tools can read/write and spawn processes; parallel worktrees do not isolate secrets or host resources. | Per-slot workspace and session, approved tool surface, tested cancellation/process reaping, and an explicit OS/container isolation policy. |
| Git publication authority | Worker-owned long-lived Git write credentials would weaken lease fencing. | One publisher boundary that checks current lease/revision before publication and reconciles uncertain remote outcomes. |
| Snapshot privacy and retention | Git artifacts are durable and can expose future CLI errors, paths or source snippets. | An allowlisted telemetry schema, redaction tests, sensitive-project retention rules and a process for rejected artifacts before any push. |
| Live rollout semantics | Existing `simulated` outcomes and process-scoped telemetry must remain distinguishable from live delivery. | A schema migration and explicit mode fields; no mass reinterpretation of historical simulations as merged features. |

This readiness audit itself is read-only and did not rerun the suite. The handoff's final verification record must retain the exact test command, Node version, count and result for the packaged revision; previously recorded results are a baseline, not a substitute for that record.

## Live delivery gate

The first live pilot should satisfy R08–R10 and R14–R21 as one continuous, observable scenario: import one ready feature from a real committed iteration; resolve its context; lease it to an authenticated chosen provider; open its draft PR immediately; implement/check it; publish both snapshots; request human review; process feedback on the same PR; and mark the task done only after verified merge. Repeat with a reporting outage, stale lease, worker restart and duplicated Git event.

Run that pilot once with Claude and once with Codex, preserving the intended subscription authentication. Docker Agent acceptance is a separate interoperability run against a pinned version. Do not claim the complete user workflow delivered until the connected scenarios pass; the mock starter and harness/MCP templates are valuable prerequisites, not substitutes for them.
