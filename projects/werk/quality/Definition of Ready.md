# Definition of Ready

A Feature Request can enter implementation only when the worker can retain all of the following:

- A stable request ID, selected registered project, title, outcome, acceptance criteria and approved file scope.
- An explicit immutable repository baseline and the exact committed project delivery policy approved by the local operator.
- The selected execution profile/provider, permitted tools, required checks, runtime limits and repair allowance.
- Completed required semantic-readiness assessment and resolved blocking questions, including configured prerequisite incorporation evidence.
- An isolated worker-owned candidate workspace and a retained start prompt; private credentials remain outside the prompt and repository.
- Available execution capacity and a confirmed shared-Git claim when shared intake is selected.

Invalid drafts remain editable. Submission is not evidence that readiness passed. A local save or commit does not replace the shared intake commit-and-push handoff. Repository policy cannot approve itself or expand machine grants.

The [delivery policy](../docs/reference/delivery-policy.md) and [request gates](../docs/reference/request-gates.md) define the versioned runtime validators. The [primary workflow contract](../docs/reference/worker-release-workflow.md) defines the downstream evidence requirements.
