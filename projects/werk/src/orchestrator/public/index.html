Systemstart, Docker oder kein Token zur Hand?

Beim Systemstart liegt der Token dieser Linie unter .werk-system/<System-ID>/lines/<Linien-ID>/credentials.json. Verwende ihren WERK_ADMIN_TOKEN, nicht den Factory-Token. Bei Windows-Docker exportiert ./werk-docker.ps1 system credentials --file system.yaml die geschützten Dateien nach .werk-system/<System-ID>/credential-export/; öffne dort lines/<Linien-ID>/credentials.json. Für eigene Dateinamen oder Zustandsordner gelten deine Startargumente.

Docker unter Windows: Führe im Release-Ordner ./werk-docker.ps1 credentials aus. Der geschützte Export liegt in .werk/credential-export/credentials.json. Beim Bash-Docker-Start liegt die Datei direkt unter .werk/credentials.json.

Beim Entwicklerstart npm run dev:fleet liegt der Token in .state/fleet/credentials.json. Beim Entwicklerstart npm run dev:factory verwende für eine Linie ihren WERK_LINE_…_TOKEN aus den Factory-Zugangsdaten. Der Factory-Token passt hier nicht.

Bei einem separat betriebenen Orchestrator erhältst du den Zugangstoken von der Person, die ihn gestartet hat. Kopiere nur den Tokenwert, ohne Anführungszeichen. Das Enrollment-Token ist für Worker bestimmt.

Aufnahme

Die API speichert den Auftrag in SQLite. Mit konfiguriertem Vault und fixiertem Git-Commit übernimmt sie Titel und Kriterien aus der Notiz. Ohne diese Bindung bleibt der Verweis ungeklärt; Kriterien werden nicht erfunden. Wiederholte Übertragung erzeugt dank Idempotenz keinen zweiten Auftrag.

Zuweisung

Ein Worker des passenden Projekts reserviert einen Auftrag. Profilwahl sowie die konfigurierten Profil- und Maschinenslots begrenzen die Vergabe.

Ergebnis prüfen

Nach dem Speichern öffnet sich das Taskboard. Wähle dort ein Feature für seine Ereignisse und die zugehörigen Snapshots.

Zielablauf mit menschlichem Review

Im Zielsystem öffnet der Worker beim Start einen Draft PR gegen den Iterationsbranch. Nach der Umsetzung fordert er Review an, bearbeitet Feedback im selben PR und beendet den Auftrag erst nach dessen Merge. Diese Git-Integration ist im Starter noch nicht verbunden.

Ready-Features einer Iteration importieren

Das Produktteam plant in Obsidian, erstellt einen Iterationsbranch mit Draft PR und markiert implementierbare Features. Der Importbefehl übernimmt diese am festgelegten Commit. Das Team kann währenddessen die nächste Iteration vorbereiten.

Verbinden, um importierte Features zu sehen.

Importbefehl und PR-Beziehung
werk-orchestrator iteration import --repo /path/to/project
  --branch iteration/2026-W42 --project demo --iteration 2026-W42
  --iteration-pr https://git.example/project/pull/10

Feature-PR: factory/FEATURE → iteration/2026-W42. Iterations-PR: iteration/2026-W42 → main. Live Git-Push/PR-Operationen sind noch nicht angebunden.
